# 命名工具链：深言能不能用，以及"聚类交给大模型"该怎么落地（2026-11-12）

## 0. 先把公司认对

你说的"深言"= **北京深言科技（DeepLang AI）**，不是 DeepSeek。核实结果：

| 项 | 事实 |
|---|---|
| 背景 | 2022-03 成立，孵化自清华 THUNLP + 北京智源（BAAI），CEO 岂凡超，首席科学家孙茂松 |
| 产品 | **语鲸**（lingowhale.com，信息获取/阅读）×  **深言达意**（shenyandayi.com，据意查词查句） |
| 主域 | `deeplang.ai` 已 502，现主域 `deeplang.net`（第三方记载，未亲测） |
| 模型 | 语鲸大模型 / LingoWhale-8B，**权重开源**（HuggingFace / ModelScope） |
| 商务 | `bd@deeplang.ai`，主要走企业定制 |

## 1. 它的 API 能干什么（这条决定方案走不走得通）

**没有找到面向开发者的公开「通用文本生成 API」。** 现有公开信息只到这一层：

- 语鲸**有开放 API**，但官网列出的能力是三类：**获取账号信息、搜索订阅频道、拉取文章**——是内容流接口，不是生成接口，更不是向量接口。
- 深言达意（据意查词）是**网页产品**，无公开 API。
- 算法备案（语鲸大模型文本生成服务算法，备案号 110108540028101240019）写明"支持 API 调用模式"，但面向**企业客户**，需要商务对接。
- LingoWhale-8B 权重开源，可本地部署——但 8B 跑命名这种任务，纯属用推土机拍蚊子。

> 一句话：**想用深言的"中文语感"做命名，走 API 不现实；走它的产品形态可行。**

## 2. 但"据意查词"恰好是命名最需要的形态

这是我核完事实后最想告诉你的一点：深言达意的核心能力**不是生成名字，是"给个意思，取回词"**（原 THUNLP WantWords 反向词典）。命名真正难的就是这一步——你心里有"离线、随身、留痕、可自持"这团意思，需要有人把它摊成一批词。

- 这条路**不需要 API**：打开 `shenyandayi.com` 输入描述，人机对话就能拿到候选。批量调 API 反而是绕远路。
- WantWords 是**开源**的（`github.com/thunlp/WantWords`，约 7.1k star，2022-02 后停更，线上版与之不同步）。可本地跑，但**依赖较老，能否直接跑起来未验证**——不要计划在这上面，除非先跑通。

## 3. 聚类到底该交给谁：分工必须划清

三条线，混在一起就会出错：

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 语义扩展（想出候选） | 深言达意 / 任意 chat 模型 | 它是"理解 + 检索"，比人拍脑袋覆盖广 |
| **聚类去重** | chat 模型 or 本地算法 | 见下 |
| **能不能用** | **只能脚本实测（RDAP + 搜索）** | 模型会把"好听"当成"可用"，这是幻觉，且 100% 会犯 |

**模型绝对不能参与判定可用性。** 已经有过实证：我凭经验说 `pitalk` 能借树莓派联想，实测四撞（其中一个是哈佛的 PiTalk、一个就长在树莓派上做语音）。模型只会把这个错误放大一百倍，因为它无法访问 `.com` 注册库，也无法区分"已注册"和"有产品在用"。

## 4. 已实现：`tools/name_cluster.py`

纯标准库、离线、无 key、可复现。两个视图：

- **形态簇**：英文用编辑距离 + 二元组，中文用字二元组，平均链接凝聚聚类。
- **高风险近似对**：英文查"少打字母就串"；中文查**共享字符**。

**为什么不用 embedding**：DeepSeek 官方没有 `/embeddings` 端点；深言没有公开向量接口。而名字是极短字符串，字形/音形特征比稠密向量更直接反映"打错就串"。

### 4.1 第一版结论是错的，值得记下来

第一版我用编辑距离判中文风险，结果 21 条里有 20 条是废话：

```
[cn] 声盒 vs 录本  编辑距离=2
[cn] 声盒 vs 留声  编辑距离=2
[cn] 声盒 vs 有底  编辑距离=2      ← 这俩毫无关系
```

**两个字的词之间编辑距离恒等于 2**，这个度量对中文两字名零信息量。改成"共享字符"后才有效：

```
[en] offlist vs offlisten  编辑距离=2   ← 真风险（已记录在案）
[cn] 声盒   vs 留声        共享字=声
[cn] 录本   vs 录匣        共享字=录    ← 这正是不该把「录本」列作备选的原因
[cn] 有底   vs 底稿        共享字=底    ← 两个候选不能同时留
```

### 4.2 语义聚类退化成全是单例（这条最重要）

13 个候选，**语义簇全部是单例**，没有一个合并。原因不是聚类算法错，是**人工打的 tag 太稀疏**（每人 2–4 个），Jaccard 达不到阈值。

这恰好反向支持你的判断：**语义聚类确实该交给大模型**——因为它的本质是"判断两个词在不在一个意思里"，靠人工标签做不出来。但要注意代价：

- 让 chat 模型一次性分组：便宜、能跑，但**结果不稳定**（同一个 prompt 跑两次分组可能不同），不能当验收依据。
- 用向量 + 层次聚类：可复现，但需要另找 embedding provider（DeepSeek 没有）。

**建议**：语义聚类只用来"给人看，帮人判断要不要撞语义场"，**不要写进任何自动决策**。

## 5. 结论

1. **深言的 API 不是这条路**——没有公开通用生成接口，语鲸开放 API 是内容类。
2. **深言的产品形态有用**：`shenyandayi.com` 的据意查词，用来把"一团意思"摊成候选词，比调 API 快。
3. **"聚类交给大模型"成立，但要限定用途**：辅助人看，不做自动判定；且要接受它不可复现。
4. **判可用性永远是脚本的事**：`name_cluster.py` 管形态冲突，RDAP 管注册状态，搜索管产品占用。三者缺一，就会重复 `pitalk` 那次错误。
